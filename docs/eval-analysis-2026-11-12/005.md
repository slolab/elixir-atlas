### Why the representation invited this choice

- Neither api.md nor the HoldsRole schema says which role kinds count as leadership of the group. `role_kind` is described as a flat list. A WP lead is attached to the Platform itself (target `initiative:data`), with the WP only in `work_item`, so "WP lead" and "Platform leadership" look like different things.
- `/api/overlap` defines leadership as including work_package_lead and task_lead, but the docs never say so. Its scope (`groups_only` means family='group', past and non-directory groups included) does not match "current Communities, Platforms and Focus Groups", so the agent had to rebuild it and re-decide the role kinds.

## Most likely fixes

1. **Add a current-directory scope to `/api/overlap`** (for example `scope=directory_current`: kind in community/platform/focus_group and status current) and **document the role kinds it counts** in api.md and in the response itself, e.g. a top-level `role_kinds: [...]`. With that scope and liaisons=true the view returns exactly the reference list, so the agent would not need to re-derive it.
2. **Add a `leadership` class to HoldsRole** (e.g. `role_class`: leadership | liaison | membership | candidate | other) with a schema description stating that Platform work-package and task leads count as Platform leadership. Agents filter on one column instead of guessing.
