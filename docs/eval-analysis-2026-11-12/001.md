## 2. Root cause

### The direction of RelatedTo hides 72% of Community–project links (components 1–4)

**Checked.** The graph holds every member of both clusters.

```sql
SELECT r.source, r.target, i.name FROM RelatedTo r
JOIN Initiative i ON i.id = CASE WHEN r.source=:p THEN r.target ELSE r.source END
WHERE (r.source=:p OR r.target=:p) AND i.kind='community';
```

- **RCI-M** (`initiative:how-we-work-scientific-programme-science-cmr-metabolomics`) links to 8 current Communities: Food and Nutrition, Galaxy, Metabolomics, Proteomics, Research Data Management, Single-Cell Omics, Systems Biology and Toxicology. All 8 have an edge where the **project is the source** and the URL is the RCI-M project page. Only Metabolomics and Systems Biology also have a Community → RCI-M edge, and those come from the Annual Report 2025.
- **DBTLHub** links to 6: Biodiversity, Metabolomics, Microbial Biotechnology, Microbiome, Research Data Management and Systems Biology. All 6 point project → Community. Only Systems Biology and Microbial Biotechnology also point Community → project (F1000 15-1717 and the Annual Report 2025).

FEGA-Connect links Federated Human Data and Proteomics. Spatial2Galaxy links Cancer Data, Galaxy, Human Copy Number Variation and Single-Cell Omics. - **Protein cluster:** the ontologies project links 3D-BioInfo and IDP, and PDBe links 3D-BioInfo and Proteomics. Both point project → Community.

**Scale, checked:**

```sql

```

150 of the 207 pairs (72%) exist only in the project → Community direction. Counting projects with two or more current Communities, a query over both directions finds 38. The agent's one-direction query found 10.

**Why the representation invites this.** The RelatedTo description the agent received (`schema_relevant.json`) is "A source names the target as involved in, linked to or the parent of the source initiative." The direction therefore records which page stated the link, not what the link means. A project page that lists its Communities produces project → Community. A Community page or report that lists projects produces Community → project. Neither the column descriptions nor api.md says to match both directions. The `/api/initiative` view does union both directions (`server/atlas_api/views.py`, the `related` query), but the skill steers agents to SQL, and this agent never called that view.

## 3. Fixes, most likely first

1. **Give group–project links one canonical direction.** Store every link between a group and a project with the project as source and the group as target, whatever page stated it, and keep the stating page in `source_url`. Alternatively, emit both directions or add a symmetric view. Update the RelatedTo description: "Direction reflects only which page states the link; match both directions." This one change fixes components 1–4 for any query shaped like this agent's, and it generalises to every overlap and partner question (020 too).
2. **Give programme areas their own kind.** Cellular and molecular research, Human data and translational research, and Biodiversity, food security and pathogens are currently `commissioned_service` with family `project`. CMR links to 14 Communities and HDTR to 5. A `programme_area` kind would keep them out of overlap queries, or let a query mark them as the rubric accepts.
3. **Add a derived pair table**, for example `SharedWork(community_a, community_b, via_kind [project|tool_tag|output|resource|community_link], via_id, via_name, source_url)`. One query would then answer overlap and partner questions, and it would include the bio.tools tag pairs and the Community–Community statements.
4. **Improve name resolution and citations.** Resolve singular and plural variants plus a parenthesised acronym ("Intrinsically Disordered Protein (IDP)"). Normalise F1000 PDF `source_url` values to the article URL.
