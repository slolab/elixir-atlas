## 2. Root causes of missed components

### C4 Labels: DATA_WRONG (misleading `basis` semantics), with a skill instruction pushing the same way

What the agent did: it built three tiers, "recommended", "mentioned or listed, but not explicitly recommended" and "catalogue/domain only". It put MEMOTE, Metabolic Atlas, MetaNetX, MNXtools and SBML in the middle tier. The rubric has two tiers: anything a Community page or paper names counts as recommended, and only catalogue tags count as catalogue-only.

Evidence, from queries on graph.sqlite:
```sql
SELECT res.name, r.basis, r.source_url FROM Recommends r JOIN Resource res ON res.id=r.target
WHERE r.source='initiative:systems-biology' AND res.id IN (...GEM resources...);
```
| Resource | basis per document |
|---|---|
| Standard-GEM | white paper `recommends`; preprint `lists` |
| MEMOTE | white paper `lists` |
| Metabolic Atlas | white paper `lists` |
| MetaNetX | white paper `lists` (kind `standard`) |
| BioModels | white paper `lists`; preprint `lists` |
| SBML | white paper `lists`; preprint `lists`; meeting report `recommends` |
| SED-ML | preprint `recommends`; white paper `lists`; meeting report `recommends` |
| FROG, MIRIAM, MIASE, scorecard | preprint `recommends` |
| COMBINE Archive, RO-Crate, SBML level 3 | preprint `lists` |

- The served schema description (trace step 14, from `007_schema_details.json`) read: *"'lists': it is only listed among the group's resources."* The agent repeated this in its answer: "the Atlas classifies this as 'lists', not an explicit recommendation". The word "only" made `lists` read as weaker than an endorsement, although every `Recommends` row is the Community's own document pointing to the resource. That is exactly the "recommended" side of the question's split.
- The served SKILL.md (still current) says: *"Distinguish … a resource listing from explicit endorsement."* This reinforces the three-tier split.
- The basis values are an LLM's reading of one quote per (resource, document), and they are inconsistent:
  - **MEMOTE** keeps the weakest white-paper sentence, cut off mid-clause ("…developed in the COMBINE context and MEMOTE"). Stronger sentences in the same paper are not used: "An advancement in this direction has been the release of the standardised genome-scale metabolic model testing tool MEMOTE", and standard-GEM "enables future automatic validation with tools such as the aforementioned MEMOTE".
  - **MetaNetX** is `lists`, but the white paper also says "Another ELIXIR effort is the established service MetaNetX". That arguably makes it `develops`.
  - **SBML/SED-ML** get `recommends` from the meeting report sentence "updating SBML and SED-ML for FAIR/CURE … principles". That is a to-do, not a recommendation.
  - **Standard-GEM** in the preprint ("for example Standard-GEM for deposition of GEMs") is `lists`.

The basis therefore works as noise for the recommended-vs-catalogue split, and the served description turned that noise into a wrong label.

Related data defects found while checking (not scored here, but they affect this question family):

- **The Community page's own recommendations are missing from the graph (DATA_MISSING, build bug).** `SELECT count(*) FROM Recommends WHERE source_url LIKE '%elixir-europe.org/communities/systems-biology%'` returns 0. `data/extracted/recommendations.jsonl` holds 6 records from `communities-systems-biology-d4e592b20d80.html`, among them the Standard-GEM bioRxiv preprint, the TeSS collection, the PBPK paper and TeSS itself. Cause: `compose.py` `documents.superseded(read)` keeps only the newest snapshot per final URL across *all* extraction types. `focus-groups-systems-biology-7cbd5b4ccb7d.html` (retrieved 11:00:04) redirects to the same URL and is newer than the communities snapshot (10:59:13), but the recommendations extractor never read the focus-groups file. All 6 records are dropped as `superseded_snapshot`. The Biodiversity Community has the same defect: 12 extracted records, 0 in the graph, superseded by `focus-groups-biodiversity-*.html`.
- **MetaNetX has no IsTool link (DATA_WRONG kind).** The resource kind is `standard`, and `TOOL_RESOURCES = {"tool","database"}` gates IsTool matching in `compose.py`. As a result `tool:metanetx` (https://bio.tools/metanetx, ELIXIR Switzerland, Tools Platform) is not linked. IsTool otherwise works: MEMOTE→tool:memote (name), Metabolic Atlas→tool:metabolicatlas (url), BioModels→tool:biomodels (url). Standard-GEM, FROG and the standards have no bio.tools entries, which is correct.

## 3. Fixes (data layer first)

1. **Collapse the agent-facing recommendation status to the question's dichotomy.** Add a derived column or view per (group, resource):
   - `named_by_group = true` whenever any `Recommends` row exists, together with the list of documents (page, white paper, preprint, report)
   - `endorsement` = strongest basis across documents
   - `catalogue_only = true` when only `ToolFor`/`IsTool` links exist

   Rename `lists` to `mentions` and describe it as "the group's own document names it for the field (counts as Community-named)". The post-run rewording goes partway. Drop or qualify the SKILL.md line "distinguish a resource listing from explicit endorsement".
2. **Fix `superseded_snapshot`.** Compute "newest" only among snapshots that the same extractor read, or alias redirect snapshots to one document. This restores the Community-page `Recommends` for Systems Biology (6) and Biodiversity (12).
3. **IsTool matching should not depend on the LLM `kind`.** Match by URL or unique name for any kind, so MetaNetX links to bio.tools/metanetx.
4. **Do not store future work as `Recommends(develops)`.** Planned items such as the RDMkit page belong in `PlanItem` only. Alternatively, add a `status` field to `Recommends` so planned items are visibly not resources yet.
5. **Expose source coverage** in `/api/release`: the catalogues included and those known to be absent (FAIRsharing, RDMkit). Agents can then state coverage gaps.
