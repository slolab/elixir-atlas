# Agentic ELIXIR API

Use the public Atlas to investigate the user's question. Read [references/api.md](references/api.md) for requests, response fields and routes through the data. No credentials or local dataset are needed. This version requires direct HTTP access to `atlas-production-d392fb6d.up.railway.app`, including JSON POST requests. At first use, request `/api/release` and state the served release. If access is blocked, report the connection failure and use the separately installed `agentic-elixir` bundled-release skill if available. Do not treat WebFetch summaries as raw records or silently mix releases.

## Search and follow connections

1. Identify the relevant topic, people, Node or Community, and time period. Resolve named entities before exploring their connections.
2. Enrich topic searches with a few short variants: synonyms, acronyms, alternative spellings and terms likely to occur in the sources. For example, try `genome-scale metabolic modelling`, `metabolic modeling`, `constraint-based modelling` and `flux balance analysis`. These are retrieval hypotheses, not evidence.
3. Search variants separately and refine using terminology in useful results. Ordinary query words are combined with AND, so appending synonyms narrows the search. Use type filters to avoid having training records crowd out projects or tools. Deduplicate by record type and ID; stop expanding when results stop adding useful evidence.
4. Prefer the precomputed records, which already join the sources: `involved_in` (one row per person and initiative: roles, leadership, plan items, outputs, tools, Nodes, organisations), `node_involved_in` (one row per Node and initiative: how it is involved, beneficiaries, its people), `shares_work_with` (groups that share a project, output, tool, leader or resource), `plan_linked_to` (a document states that one project's work item complements or builds on another's) and the initiative fields `leaders`, `limits`, `recent_activity`, `latest_own_activity` and `scope`. For a named group or project, read `/api/initiative?id=...`; for a Node, `/api/node?id=...`; for a person, `/api/person?id=...`. Read each section you need in full. Check `/api/release`; when `api.sql` is true, discover tables with `/api/schema?format=sql&detail=summary` (table names have no underscores, e.g. `involvedin`, `sourcestatement`) and fetch facts with batched SQL, including IDs and source URLs. Check truncation and correct queries from returned errors.
5. Establish the requested population before counting or claiming absence. Kinds `community`, `platform` and `focus_group` hold only the groups the ELIXIR directory pages list, with status `current` or `past`; `became` edges record transitions such as a Focus Group becoming a Community. National and external groups are `node_group` or `other_group`; `programme_area` is a Scientific Programme area, not a project. For whether a project has ended, use `period_status` (ended, running, not_started at the snapshot), not `status`. `related_to` is stored in both directions, so query one side and count distinct initiatives. Keep uncertain inclusion explicit.

## Answer from evidence

- State what the evidence cannot show. Each view's `limits` lists what is not public or not collected (member lists, grant agreements, effort and pay, uncollected sources such as FAIRsharing, RDMkit and Slack); repeat every limit that bears on the question, and say so explicitly when something is missing, unstated or not public rather than leaving it out. When you conclude that nothing matches (no other group documents it, no person leads it, no dates are given), write that conclusion.
- For people, name them with their role, organisation and Node. For contacts, give the group's mailbox and the named co-leads and liaison. For a person's or Node's involvement, list every role and plan item, including governance roles and participation.
- Verify each requested claim against source statements, relationship evidence and plan items. Before answering, check that each requested field is supported or explicitly unavailable. Aggregated contacts, dates and roles can combine different sources or subgroups. Preserve source wording such as co-lead, interim, planned and reported; compare conflicting statements instead of relying only on the merged value. Cite original URLs or DOIs.
- Distinguish commitments from delivered outputs, a person's role from their Node's obligation, and a resource listing from explicit endorsement. Check the `basis` of links: a Node that `takes_part_in` with basis `own_page` is on the initiative's current official page, `stated` comes from another source (an older page, a Node site or a plan) and `lead_node` is only the Node of one of its leads; an output linked by `description` only names the group in its description. Every `recommends` edge is a recommendation by the group's own page or paper; a bio.tools tag or TeSS listing alone is a catalogue entry. State funding or in-kind status only where a source says it. Do not infer staff effort from roles.
- Separate overlaps a source states (a plan link, a shared project, output, tool or leader) from candidates that only share a topic, and label the latter as inferred.
- For activity or progress, use dated events, outputs and statements. A year-only or month-only date cannot be placed before or after a day cutoff inside that year or month; say that it is undetermined. Retrieval dates are not activity dates. Search for named mentions in outputs, related projects and statements as well as direct links; missing graph edges do not establish absence. Report the latest evidence and coverage limits; missing public evidence does not establish inactivity or a capability gap.
- Fit the answer to the requested task: contacts and overlaps, commitments and reporting, resources grouped by type, or roadmap and handover material. Label proposed activities as proposals and identify missing evidence instead of filling gaps with assumptions.
